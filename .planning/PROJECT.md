# AI-Driven Portfolio Advisor

## What This Is

A personal investment portfolio advisor that turns a 12-field investor profile into a recommended ETF allocation via a 4-stage ML pipeline, then lets the user fine-tune that allocation through a conversational chat interface backed by a closed set of LLM tools. This is a migration of an existing single-file Streamlit prototype (the "AI Financial Advisor" project) into a 3-tier production-grade architecture: Next.js (App Router) + Supabase Postgres + Python FastAPI.

## Core Value

A user fills in 12 financial profile fields, sees an ML-recommended ETF portfolio they can trust, and can conversationally adjust it — without the LLM ever silently overriding the model. The frozen ML baseline is always visible alongside the live, user-tuned allocation.

## Context

**Migration origin.** The product began as a 4th-year IE student final project ("AI Financial Advisor") implemented as a Streamlit single-page app. The Streamlit prototype already implements the full 4-stage ML pipeline:

1. Stage 1 — Risk profile classification (RandomForest, 19 engineered features → Aggressive / Moderate / Conservative)
2. Stage 2 — Asset allocation regression (MultiOutput RF → `equity_pct`, `bond_pct`)
3. Stage 3 — ETF count regression (RandomForest → total ETFs per class)
4. Stage 4 — Rule-based ETF selection (AUM-weighted sampling + conflict resolution in `src/allocations.py`)

**What's changing.** State, UI, and LLM chat move to a Next.js + Supabase stack. The financial brain — the 4-stage pipeline plus real-time ETF price fetching (yfinance + Finnhub) — stays in Python and is exposed via a thin FastAPI wrapper. This is intentional: the legacy ML/financial logic is not being rewritten in TypeScript.

**Codebase facts.** Python 3.14.2, no lockfile (only `requirements.txt` with `>=` pins), no Dockerfile, scikit-learn 1.3+, openai 1.30+, yfinance, Streamlit (to be retired). Models and data artifacts (`data/`, `models/`, `evaluation_reports/`) are gitignored and must be regenerated via `python pipeline.py`. See `.planning/codebase/` for full ARCHITECTURE/STACK/STRUCTURE/CONVENTIONS/TESTING references.

**Known model performance baseline.** Stage 1 risk profile classifier sits at ~46% test accuracy (vs 33% random baseline for 3 classes) — label noise from circular labeling (labels generated by the same rule-based allocations.py the ML is meant to predict) is the dominant bottleneck. This is a known limitation accepted for the migration; improving the model is a separate workstream from this architectural migration.

**Repo layout.** Monorepo. The Python ML brain stays at the repo root (`src/`, `pipeline.py`, etc.). The FastAPI wrapper is added inside the same repo. The Next.js frontend lives in `frontend/` (currently empty). A single `.planning/` at the repo root governs the whole migration.

**Spec source.** `docs/MIGRATION-SPEC.md` (PRD, manifest-override, precedence=2, treated as locked-ish for the architectural assertions captured in Key Decisions below).

## Constraints

- **Tech stack (frontend)**: Next.js App Router + TypeScript + Tailwind CSS + Shadcn/ui + Recharts or Tremor + Zod (locked by `DEC-frontend-stack`)
- **Tech stack (backend)**: Python 3.14, FastAPI wrapping the existing 4-stage scikit-learn pipeline (no Python rewrite) — `CON-financial-brain-stays-python`
- **Tech stack (data)**: Supabase Postgres only; no other persistence layer for this milestone
- **API surface**: v1 FastAPI surface is exactly 4 endpoints — `POST /api/recommend`, `POST /api/current-prices`, `POST /api/explain`, `GET /api/etfs/{ticker}` — `DEC-fastapi-endpoint-surface`
- **Database schema**: Exactly 4 tables (`profiles`, `portfolios`, `portfolio_history`, `chat_messages`), single SQL migration file paste-runnable in Supabase SQL Editor — `DEC-db-tables-fixed`, `CON-single-sql-migration-file`
- **Profile schema**: Exactly 12 investor fields with specific types/enums, frozen across frontend form / DB / ML pipeline — `DEC-investor-profile-schema-frozen`
- **LLM tool surface**: Closed set of 7 tools (3 read-only, 4 mutating), no others — `DEC-llm-tools-closed-set-v1`, `CON-llm-tool-surface-is-closed-set`
- **State isolation**: `ml_result` immutable except via `update_investor_profile`; `current_allocation` only mutated by `adjust_allocation`; comparative banner must render when they diverge — `CON-state-isolation-invariants`
- **Repo layout**: Monorepo, Python at root, Next.js in `frontend/`, single `.planning/` at root
- **Dependencies**: yfinance for live prices (Python side only), OpenAI via Vercel AI SDK for chat, Finnhub for ETF metadata enrichment (existing). All API keys via `.env` (gitignored)
- **Compatibility**: Must not break the existing `python pipeline.py` training entry point or the existing `src/inference.py` inference CLI — they remain as Python-internal artifacts the FastAPI layer wraps

## Open Questions / First-Week Decisions

<!-- INFO-level open questions surfaced by the synthesizer. Not blocking, but should be resolved early in execution. Full report at .planning/INGEST-CONFLICTS.md. -->

1. **Single-source synthesis caveat.** All intel derives from one PRD (`docs/MIGRATION-SPEC.md`). If future ADRs or SPECs ingest later they may contradict assertions here; precedence rules will re-evaluate. — No action required now.

2. **PRD asserts ADR-level "decisions" without ADRs.** Several items (3-tier, 12-field profile, 4-table schema, 2-tool LLM surface, baseline-vs-current state, Vercel AI SDK) read like ADR-level decisions but live inside a PRD (precedence 2, not `locked: true`). They are written here as locked-ish with explicit provenance. — If protection against future PRD churn is desired, promote them to standalone ADRs with `locked: true` and re-ingest.

3. **`adjust_allocation` delta semantics under-specified for non-equity/bond classes.** Spec gives `equity_delta` and `bond_delta` as examples but does not enumerate the full set of allowable delta keys (cash, alternatives, international, etc.), the renormalization algorithm when multiple deltas conflict, or clamp behavior if a delta would push a class outside [0, 1] before renormalization. — Resolve before Phase 5 starts. Land on a delta-key taxonomy + clamp/renormalize order.

4. **`update_investor_profile` "wipes qualitative overrides" — provenance of `current_allocation` is implicit.** After a factual profile update, `ml_result` is replaced and qualitative overrides are wiped — so presumably `current_allocation` is reset to equal the new `ml_result`. Implied but not stated verbatim. — Confirm and make explicit in Phase 5 implementation (likely: `current_allocation := new ml_result` on `update_investor_profile`).

5. **Monorepo confirmed (resolved).** Per user input 2026-05-18: monorepo layout with Python at root and Next.js in `frontend/`. No further decision required — recorded in Key Decisions above.

6. **No explicit auth/RLS or multi-user isolation policy stated.** `profiles` is linked to `auth.users`, implying Supabase auth + per-user data, but no Row-Level Security policies, ownership constraints on `portfolios` / `portfolio_history` / `chat_messages`, or auth-flow UX are specified. — Resolve during Phase 2 (database init) and Phase 3 (frontend scaffold). Recommended: enable RLS on all 4 tables with per-user `auth.uid()` ownership constraints; decide sign-up / sign-in UX before Phase 3.

**Analysis Date:** 2026-05-18

## Tech Debt

**Circular label generation (architectural):**
- Issue: ML training labels are generated by the same rule-based logic (`run_allocations_pipeline`) the models are meant to approximate. The stochastic `np.random.choice` on line 301 of `src/allocations.py` samples risk profiles from probability distributions rather than assigning them deterministically. Each pipeline run produces different labels for the same investor inputs.
- Files: `src/allocations.py:301`, `src/prepare_data.py:92`
- Impact: Irreducible label noise is the ceiling on Stage 1 accuracy (~46%). The ML models cannot out-learn a noisy oracle. Stage 2 R² ≈ 0.06 (near zero) is a direct consequence of the same noise propagating to allocation targets via `get_allocation_mix`.
- Fix approach: Replace stochastic label generation with deterministic label assignment — use `argmax` on the probability dict rather than `np.random.choice`. This eliminates noise without changing the domain logic. Alternatively, treat the probability dict itself as a soft label and train with label smoothing.

**Duplicate `_map_to_asset_class` / `get_category_mapping` functions:**
- Issue: `src/data_validation.py:185-195` and `src/allocations.py:126-140` implement the same category-to-asset-class mapping logic. They must stay in sync manually.
- Files: `src/data_validation.py:185`, `src/allocations.py:126`
- Impact: If one function is updated (e.g., adding a new ETF category keyword), the other silently diverges. ETFs would then be imputed against medians for the wrong asset class at training time.
- Fix approach: Extract the mapping into `src/validation_rules.py` (already the shared contract module) and import it in both files. A drift test exists in `tests/test_data_validation.py:329` as a partial guard, but it only covers a static list of sample categories.

**Stage 3 ML prediction is unused at inference time:**
- Issue: `src/inference.py:208-213` runs the `count_regressor` to produce `total_pred`, clips it to `[7, 13]`, and stores it as `total_etfs`. But the per-class ETF counts (`num_equity`, `num_bond`, `num_alt`) that actually drive portfolio construction come from a separate stochastic call to `get_num_etfs()`. The ML-predicted `total_etfs` and the sum of `etf_counts` diverge silently.
- Files: `src/inference.py:208-213`, `src/allocations.py:113-123`
- Impact: The ML model (Stage 3) has no actual effect on the portfolio returned to the user. The displayed `total_etfs` metric on the UI may differ from the actual count in `portfolio`.
- Fix approach: Either derive per-class counts from the ML total using a fixed ratio, or drop Stage 3 ML and use `get_num_etfs()` directly, documenting it as rule-based.

**`allocations.py` exception silently falls back to random pick:**
- Issue: Lines 234-239 catch all exceptions during the weight-calculation loop and fall back to `np.random.choice` with uniform weights, discarding AUM and star-rating weighting entirely with no log.
- Files: `src/allocations.py:234-239`
- Impact: Any ETF with unusual data (zero AUM, NaN volatility after imputation gap) causes silent quality degradation in the portfolio. The fallback is invisible in production.
- Fix approach: Log a warning at minimum. The data validation layer now imputes these values, so the exception path should rarely trigger; add an assertion to confirm.

**Notebooks duplicated with `wide_params` suffix:**
- Issue: `notebooks/phase3B_allocation_regression_experiments wide_params.ipynb` and `notebooks/phase3C_etf_count_regression_experiments wide_params.ipynb` exist alongside their originals. These are diverged experiment copies with no clear canonical version.
- Files: `notebooks/phase3B_allocation_regression_experiments wide_params.ipynb`, `notebooks/phase3C_etf_count_regression_experiments wide_params.ipynb`
- Impact: Ambiguity about which notebook produced the saved models. Notebook outputs may show different metrics than what `src/train_models.py` would reproduce.
- Fix approach: Delete or archive the `wide_params` copies; encode the wider parameter grid into `src/train_models.py` with a comment.

## Known Bugs

**`total_etfs` vs `sum(etf_counts)` inconsistency displayed in UI:**
- Symptoms: `app.py:206` displays `ml_result["total_etfs"]` from the ML prediction. The actual ETF tickers shown in the portfolio derive from `etf_counts`, whose sum may differ.
- Files: `src/inference.py:209-232`, `app.py:206`
- Trigger: Every inference call, since `total_etfs` comes from clipped ML prediction and `etf_counts` comes from independent stochastic `get_num_etfs()`.
- Workaround: None. The displayed "Total ETFs" metric is cosmetically incorrect.

**`prepare_data.py` always picks the most-recent investor CSV by timestamp:**
- Symptoms: Running `src/data_generation.py` twice without cleaning `data/processed/` produces a second timestamped file. `prepare_data.py:45` picks the latest one, silently ignoring the earlier.
- Files: `src/prepare_data.py:42-45`
- Trigger: Re-run `src/data_generation.py` without deleting `data/processed/`.
- Workaround: Manually delete old CSVs before regenerating.

## Security Considerations

**Prompt injection via unvalidated user-facing string fields:**
- Risk: The LLM system prompt in `src/llm.py:113-118` interpolates all 12 investor profile fields directly into the prompt string. Fields like `InvestmentGoal`, `MaritalStatus`, and `Education` are validated against an allowed-values list by `validate_input`, so adversarial free-text is not possible through the form. However, the `update_investor_profile` tool (`src/llm.py:60-92`) accepts an `updates` dict with arbitrary string values and passes them to `recommend()` with validation. If the LLM is instructed via chat to set `InvestmentGoal` to a crafted string, the validation layer would catch it — but tool `reason` field is interpolated into `tool_result` without any sanitisation (`app.py:279`).
- Files: `src/llm.py:113-118`, `app.py:274-280`
- Current mitigation: `validate_input` enforces allowed values for all categorical fields before ML pipeline runs.
- Recommendations: Sanitise the `reason` field before including in tool result strings; it is currently passed verbatim to the LLM in the next turn.

**No `.env.example` file:**
- Risk: New collaborators or deployment environments have no documented list of required secrets. The required keys (`OPENAI_API_KEY`, `FINNHUB_API_KEY`) are only visible by reading source code.
- Files: `src/llm.py:18`, `src/etf_fetcher.py:175`
- Current mitigation: None.
- Recommendations: Add `.env.example` with placeholder values and commit it.

**`OPENAI_API_KEY` silently `None` at module import:**
- Risk: `src/llm.py:18` calls `os.environ.get("OPENAI_API_KEY")` at module load time. If the key is absent, `client` is constructed with `api_key=None`. The first API call will fail at runtime rather than at startup.
- Files: `src/llm.py:18`
- Current mitigation: `app.py:122-123` catches the exception and falls back to a static explanation string. The chat feature silently stops working.
- Recommendations: Add a startup check that raises `EnvironmentError` with a clear message if the key is missing.

## Performance Bottlenecks

**ETF data fetch: 95 sequential HTTP calls with 1 s sleep each:**
- Problem: `src/etf_fetcher.py:37` sleeps 1 second between every Finnhub API call. With 95 ETFs, this is at minimum 95 seconds of blocking I/O just for Finnhub quotes, plus yfinance calls (10-year history per ETF).
- Files: `src/etf_fetcher.py:23-42`, `src/etf_fetcher.py:156-167`
- Cause: Rate-limit avoidance, but implemented as a fixed sleep with no adaptive backoff.
- Improvement path: Use `concurrent.futures.ThreadPoolExecutor` for yfinance calls (which are stateless); keep Finnhub sequential with adaptive backoff using `tenacity` or `backoff`.

**`run_allocations_pipeline` uses `DataFrame.apply` row-by-row for 5000 investors:**
- Problem: `src/allocations.py:299-314` runs Python-level loops for every investor via `apply()`. `assign_portfolio_numeric_aum` itself is a nested loop that builds `candidate_df` copies for each investor.
- Files: `src/allocations.py:299-314`, `src/allocations.py:173-243`
- Cause: Conflict-resolution logic inherently requires per-investor state, but the outer `apply` prevents any vectorisation.
- Improvement path: Acceptable at 5000 rows for a research project. For production scale, precompute the probability weights per asset class once and cache; the inner loop is the real cost.

**Module-level artifact cache is not thread-safe:**
- Problem: `src/inference.py:106-112` uses a global `_ARTIFACTS = None` sentinel with a check-then-set pattern. In a multi-user Streamlit deployment, two simultaneous requests could both see `None`, trigger two concurrent `_load_artifacts()` calls, and race to assign `_ARTIFACTS`.
- Files: `src/inference.py:106-112`
- Cause: Standard singleton pattern without a lock.
- Improvement path: Wrap with `threading.Lock` or move to `@st.cache_resource` in `app.py`.

## Fragile Areas

**All scripts assume CWD is project root:**
- Files: `src/prepare_data.py:27-38`, `src/train_models.py:47-50`, `src/inference.py:42-44`, `pipeline.py:41`
- Why fragile: All paths are bare relative strings like `'data/training'`, `'models'`. Running any script from a different working directory silently fails with `FileNotFoundError`.
- Safe modification: Replace bare relative paths with `Path(__file__).parent.parent / 'data' / 'training'` (the pattern used correctly in `src/data_generation.py:304` and `src/etf_fetcher.py:297`).
- Test coverage: No test exercises path resolution. `src/inference.py` will silently fail at `joblib.load` if called from a subdirectory.

**`pipeline.py` invokes child scripts via `subprocess.run` instead of importing:**
- Files: `pipeline.py:50-54`, `pipeline.py:119-124`, `pipeline.py:146-149`, `pipeline.py:173-175`
- Why fragile: Subprocess invocations cannot propagate Python exceptions, do not share the virtual environment robustly across OSes, and make debugging harder (stack traces are not propagated). Step 3 and Step 4 calls do not capture `stdout`/`stderr`, so failure messages are swallowed.
- Safe modification: Import the module-level logic from each script into `pipeline.py` and call it directly. `src/prepare_data.py` and `src/train_models.py` are already structured as top-level scripts with no `if __name__ == '__main__'` guard, which is what makes direct import viable.
- Test coverage: `pipeline.py` has no tests.

**yfinance API breakage risk:**
- Files: `src/etf_fetcher.py:76-112`
- Why fragile: `requirements.txt` pins `yfinance>=0.2.0` (any version above 0.2). yfinance has a history of breaking `info` dict key names between minor versions (e.g., `category`, `totalAssets`, `fundFamily` have all changed in past releases). The `funds_data` attribute used in `fetch_fund_operations` (`src/etf_fetcher.py:114-133`) is particularly unstable.
- Safe modification: Pin to a specific yfinance version (e.g., `yfinance==0.2.51`). Add a smoke test that asserts the expected keys are present after fetching one ticker.
- Test coverage: None. No tests for ETF fetching.

**Morningstar ratings require all three return periods:**
- Files: `src/morning_star_rating.py:13-14`
- Why fragile: `calculate_star_ratings` silently drops ETFs missing 1Y, 3Y, or 5Y returns. Newer ETFs (e.g., `CGDV`, launched 2022; `DYNF`) that lack 5-year history receive `NaN` ratings. These ETFs fall through to `fillna(3)` in `run_allocations_pipeline` and `inference.py`, artificially equalising their quality score with average-rated ETFs.
- Safe modification: Implement a partial-history rating (e.g., use 1Y+3Y only if 5Y is unavailable) rather than silently downgrading to the median star rating.
- Test coverage: `morning_star_rating.py` has no tests.

## Scaling Limits

**ETF universe fixed at ~95 hard-coded tickers:**
- Current capacity: 95 ETFs defined in `src/etf_fetcher.py:184-280`.
- Limit: Adding ETFs requires editing the source list and re-fetching. The conflict-group list in `src/allocations.py:11-20` also requires manual update.
- Scaling path: Move the ticker list and conflict groups to a config file (JSON or YAML) loaded at runtime.

**Synthetic investor dataset fixed at 5000 rows:**
- Current capacity: `N = 5000` hard-coded at `src/data_generation.py:9`.
- Limit: The training set is small for 19 features; Random Forest models show high variance. Increasing N improves label stability but doesn't fix the noise source.
- Scaling path: Parameterise N via CLI argument; regeneration is fast (<5 seconds).

**Unbounded LLM chat history per session:**
- Current capacity: Each session accumulates every message, tool call, and tool result in `st.session_state["chat_history"]`.
- Limit: `gpt-4o-mini` has a 128k context limit. After ~200 back-and-forth turns (including tool artifacts), the context window will be exceeded and API calls will fail with a `400` error that the app does not handle.
- Scaling path: Implement a sliding window that retains the last N messages, or summarise older turns into a compressed context block.

## Dependencies at Risk

**`yfinance>=0.2.0` (unpinned, unstable API):**
- Risk: yfinance has no stable public API contract. Breaking changes to `info` dict keys occur without major version bumps.
- Impact: `src/etf_fetcher.py` would silently collect `None` values for renamed keys, producing corrupt training data.
- Migration plan: Pin to a tested version. Consider `OpenBB` or a commercial data provider for production.

**`finnhub-python>=2.4.0` (rate-limited free tier):**
- Risk: Finnhub free tier allows 60 calls/minute. With 95 ETFs and 1s sleep, the current code stays just under the limit, but any quota change breaks the fetch.
- Impact: `src/etf_fetcher.py:175-183` exits early if the key is absent. If rate-limited mid-fetch, the partial DataFrame is still saved, producing a corrupt ETF file without warning.
- Migration plan: Add response status checking; save partial results as a recoverable checkpoint.

**`scikit-learn>=1.3.0` (unpinned, model serialisation risk):**
- Risk: `joblib`-serialised sklearn models are only compatible within the same major sklearn version. Loading a model trained with `sklearn 1.3` under `sklearn 1.5+` may fail or produce silent mispredictions.
- Impact: If the environment is upgraded, `src/inference.py` will fail at `joblib.load` with an obscure error.
- Migration plan: Pin to a specific sklearn minor version. Include the sklearn version in `label_map.json` so mismatches can be detected at load time.

## ML-Specific Risks

**`risk_tolerance` feature is a near-proxy for the Stage 1 label:**
- Risk: `risk_tolerance` (Low/Medium/High) is included as a training feature (`src/prepare_data.py:102`) and the Stage 1 label is `risk_profile` (Conservative/Moderate/Aggressive). These two variables are derived from the same underlying `risk_score` in `src/data_generation.py:209-216` (quantile binning). The ML model is effectively learning a one-step lookup, which inflates apparent accuracy but contributes little generalisable signal.
- Files: `src/prepare_data.py:99-108`, `src/data_generation.py:192-216`
- Impact: Model appears better than it is on the synthetic dataset; on real user data where `risk_tolerance` is self-reported and noisier, performance would degrade further.
- Severity: HIGH (academic validity concern).

**No random seed in `src/allocations.py`:**
- Risk: `src/allocations.py` uses `np.random.choice` and `np.random.normal` extensively (lines 93-95, 116-123, 219, 237, 301) with no seed. Each run of `prepare_data.py` generates different labels. While `src/data_generation.py` seeds with `np.random.seed(42)`, this is a module-level call that does not persist through subsequent `import` calls in a fresh subprocess.
- Files: `src/allocations.py`, `src/prepare_data.py:92`
- Impact: Training is not reproducible. Two successive pipeline runs produce models with different performance metrics.
- Fix approach: Add `np.random.seed(42)` at the top of `src/allocations.py` or accept a seed parameter in `run_allocations_pipeline`.

**IBIT (Bitcoin ETF) included in equity universe:**
- Risk: `IBIT` is listed in the ETF ticker list (`src/etf_fetcher.py:206`). Its yfinance category is likely `"Digital Assets"` or similar, which matches no keyword in `get_category_mapping` and falls through to the `'equity'` default. IBIT then competes with broad equity ETFs (VOO, VTI) for selection in the equity portion of conservative and moderate portfolios.
- Files: `src/etf_fetcher.py:206`, `src/allocations.py:126-140`
- Impact: Conservative investors could receive IBIT in their equity allocation, which is financially inappropriate for the stated risk profile.
- Fix approach: Add `'digital'` and `'bitcoin'` to the alternative keywords in `get_category_mapping`, or explicitly exclude IBIT from conservative/moderate portfolio selection.

**`TQQQ` (3x leveraged ETF) not excluded from any risk profile:**
- Risk: `TQQQ` is listed at `src/etf_fetcher.py:257` and included in the equity pool. It belongs to the `CONFLICT_GROUPS` entry `['QQQ', 'QQQM', 'TQQQ']`, meaning it competes with QQQ for selection. TQQQ is a 3x leveraged ETF and is unsuitable for all but the most sophisticated aggressive investors.
- Files: `src/etf_fetcher.py:257`, `src/allocations.py:13`
- Impact: Any investor profile could receive TQQQ as an equity holding. Moderate and conservative investors are particularly exposed.
- Fix approach: Remove TQQQ from the ETF universe or add a `leveraged_exclusion` flag and filter it out unless risk profile is Aggressive with `FinancialInvolvement=High`.

**Stage 2 regression R² ≈ 0.06 masked by post-hoc clipping:**
- Risk: `src/inference.py:187-195` applies `PROFILE_BOUNDS` hard clips on allocation predictions. With R² near zero, the model is essentially predicting noise, and the bounds do the real work. The ML model in Stage 2 adds no meaningful signal over the rule-based bounds.
- Files: `src/inference.py:187-195`, `src/train_models.py:329-378`
- Impact: Presenting Stage 2 as an ML allocation model is misleading; the bounds are the true allocator.
- Fix approach: Document this explicitly. Consider replacing Stage 2 with deterministic allocation from PROFILE_BOUNDS directly, or address label noise first (see circular label concern above).
